# Distributed Job Scheduler

A production-inspired distributed job scheduling platform: authenticate, create
projects and queues, submit immediate/delayed/scheduled/recurring/batch jobs
through a REST API, and watch a fleet of worker processes atomically claim,
execute, retry, and dead-letter them — all visible live on a dashboard.

```
backend/    FastAPI + PostgreSQL API, worker process, scheduler process, tests
frontend/   React + Vite dashboard (WebSocket live updates)
docs/       Architecture, ER diagram, API docs, design decisions
docker-compose.yml       full stack: postgres, api, scheduler, 2 workers, frontend
docker-compose.test.yml  scratch postgres for the test suite
```

Read `docs/ARCHITECTURE.md`, `docs/ER_DIAGRAM.md`, `docs/API_DOCUMENTATION.md`,
and `docs/DESIGN_DECISIONS.md` for the write-ups this assignment asks for.

## Quick start (Docker — recommended)

```bash
git clone <this repo> && cd scheduler
docker compose up --build
```

This brings up Postgres, the API (`:8000`), a standalone scheduler process,
two worker processes (`worker-1` watching `emails,reports`, `worker-2`
watching `emails`), and the dashboard (`:3000`).

Seed demo data (creates a login + a project with two queues):

```bash
docker compose exec api python scripts/seed.py
```

Open **http://localhost:3000** and log in with:

```
email:    demo@example.com
password: password123
```

API docs (Swagger UI, auto-generated by FastAPI): **http://localhost:8000/docs**

## Running without Docker

### Backend

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # edit DATABASE_URL if not using the default local postgres

# start a local postgres however you like, e.g.:
docker run -d -p 5432:5432 -e POSTGRES_USER=scheduler -e POSTGRES_PASSWORD=scheduler -e POSTGRES_DB=scheduler postgres:16-alpine

python scripts/seed.py          # creates tables + demo user/project/queues
uvicorn app.main:app --reload   # API on :8000, embedded scheduler loop runs alongside it
```

Start one or more workers in separate terminals:

```bash
# get a token first (or reuse one from the dashboard's browser localStorage)
TOKEN=$(curl -s -X POST localhost:8000/api/v1/auth/login \
  -d "username=demo@example.com&password=password123" \
  -H "Content-Type: application/x-www-form-urlencoded" | python -c "import sys,json;print(json.load(sys.stdin)['access_token'])")

SCHEDULER_TOKEN=$TOKEN python scripts/run_worker.py --name worker-1 --queues emails,reports --concurrency 4
```

(Optional) run the scheduler as its own process instead of relying on the
API's embedded loop:

```bash
python scripts/run_scheduler.py
```

### Frontend

```bash
cd frontend
npm install
cp .env.example .env   # VITE_API_URL, defaults to http://localhost:8000
npm run dev             # dashboard on :5173
```

## Running tests

Atomic-claim tests need real PostgreSQL row locking, so they run against a
throwaway Postgres container rather than SQLite:

```bash
cd backend
docker compose -f ../docker-compose.test.yml up -d
pip install -r requirements.txt
pytest -v
```

`tests/test_concurrent_claim.py` is the key reliability test: it fires 10
concurrent claim calls, each on its own DB connection, against 30 queued jobs
and asserts every job is claimed by exactly one worker.

## Trying it end-to-end

1. Log in to the dashboard, open **Queues**, create a project (or use the
   seeded "Demo Project") and a queue.
2. Open the queue, submit a few immediate jobs named `send_email` with
   payload `{"to": "test@x.com"}` — the demo worker handlers understand
   `send_email` and `generate_report`; any other job name runs a generic
   echo handler.
3. Submit a job with payload `{"simulate_failure": true}` to watch it retry
   with exponential backoff and eventually land in the **Dead letter** tab,
   where you can requeue it.
4. Create a **Recurring** schedule with a cron expression like `*/2 * * * *`
   and watch new job instances appear every two minutes.
5. Open **Workers** to watch heartbeats and live claim activity pulse in via
   WebSocket.

## What's implemented vs. bonus scope

Implemented: WebSocket live updates, basic RBAC (org roles), rate limiting
(slowapi, per-IP), idempotency keys, and distributed locking for job claims
(`SELECT ... FOR UPDATE SKIP LOCKED`, which *is* the distributed-locking
mechanism here since all claim traffic goes through Postgres).

Explicitly out of scope for this pass — see `docs/DESIGN_DECISIONS.md` for
why and how each would be added: workflow/DAG dependencies between jobs,
queue sharding across multiple databases, a message-bus-based event-driven
execution path, and AI-generated failure summaries.
